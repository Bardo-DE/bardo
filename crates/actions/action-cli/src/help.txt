bardo-do: drive any Bardo app from a command line.

Usage:
  bardo-do apps                                  installed apps with manifests
  bardo-do skills                                installed skills the assistant may load
  bardo-do <app> --list                          its actions: name, effect, parameters
  bardo-do describe <app> <action> [--json]      JSON Schema of the parameters
  bardo-do <app> <action> [<thing>...] [--<param> <value>]... [--dry-run] [--json] [--session <id>]
  bardo-do <app> search <text> [--json]          search the app's things
  bardo-do <app> context [--json]                what the app shows now
  bardo-do undo <undo-id> | --last               take back what this terminal did
  bardo-do ask [--space <id>] <text> [--json]    talk to the assistant; prints its answer
  bardo-do sessions                              the stored sessions this terminal may bring back
  bardo-do sessions load <id> [--json]           one session's turns and calls
  bardo-do sessions fork <id> [--at <row>]       a new session keeping the log up to a row

<app> is the app's slug (notes, anyview, shell) or its full name; <action> drops the app's
prefix (note.archive for notes.note.archive). Things are <kind>:<key>, or #<n> for text an
earlier command held. A text parameter given as `-` reads standard input. Dates are RFC 3339.

Every call goes through bardo-actiond's gate: a read runs, anything else asks the person on screen
unless they chose "Allow from the terminal: this action, until logout" on that sheet. There is
no flag that skips the question.

`ask` is the assistant's conversation from a terminal: it prints the answer, the plan steps and
what the answer was made of. It never answers a confirmation: when one is waiting it says so and
exits 8, and the confirmation is answered on sill's sheet.

Output is text on a terminal, and JSON with --json or when stdout is not a terminal:
  {vocab, outcome, undo, entities, handles}; a failure is {vocab, error}.
